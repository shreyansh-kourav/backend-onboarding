# Secure File Uploads (FastAPI)

## Core principle
Filename, extension, `Content-Type`, and contents are all client-controlled. Only the actual bytes tell you what a file is.

## Risks

- **Malware / web shells:** uploaded script lands where the server executes it
- **Path traversal:** `../../etc/passwd` in a client-supplied filename
- **Stored XSS:** SVG/HTML with scripts served from your own domain
- **Zip bombs / decompression bombs:** tiny file expands to huge size
- **Resource exhaustion:** huge or endless uploads fill disk

## Defenses

### In app code

- Enforce a **size limit** (streaming byte counter, not just `Content-Length`)
- **Allowlist extensions** AND verify **magic bytes** (and that they match the extension)
- **Generate own filenames** (`uuid4().hex`); never use the client's name in a path
- Store **outside the web root** (or in private object storage)
- Write to a temp file, validate, then publish atomically with `os.replace`
- On download: validate the ID with a regex, check authorization, set our own MIME type
- Safe download headers:
  - `X-Content-Type-Options: nosniff`
  - `Content-Disposition: attachment`
  - `Content-Security-Policy: default-src 'none'; sandbox`
- Images: re-encode with Pillow and set `Image.MAX_IMAGE_PIXELS` to defeat decompression bombs and polyglot files
- Leave **SVG/HTML off the allowlist** (or sanitize / serve as download only)

### In infrastructure

- **Body size limit at the reverse proxy:** nginx `client_max_body_size 5m;`
- **Separate domain** for user content (e.g. `usercontent.example.com`) so scripts can't touch app cookies
- **Malware scanning** (ClamAV via `clamd` / `pyclamd`)
- **Object storage** (S3 etc.) with presigned URLs and a `content-length-range` policy
- Rate-limit the upload endpoint
- Point `TMPDIR` at a dedicated volume with a quota
- **Archives:** avoid extracting; if you must, cap total size, file count, and ratio, and block zip-slip (entries escaping the target dir)

## Key gotcha: FastAPI parses the body BEFORE your handler runs

1. `UploadFile = File(...)` makes FastAPI call Starlette's multipart parser first
2. The parser reads the **entire body** into a `SpooledTemporaryFile` (memory up to 1 MB, then a real file in `/tmp`)
3. Only then does your handler run, so a size check there is too late to prevent a 5 GB spool to disk
4. Your `unlink` cleanup deletes your copy, not Starlette's temp file

### Fixes (in order of preference)

1. Proxy limit (`client_max_body_size`)
2. ASGI middleware that checks `Content-Length` and counts bytes while streaming
3. Bypass the form parser: `request.stream()` + `streaming-form-data`
4. Direct-to-S3 uploads with presigned POST
5. Dedicated `TMPDIR` volume

## Why a pre-check on size isn't enough

- `Content-Length` can be wrong or missing (`Transfer-Encoding: chunked`) and covers the whole multipart body
- Use it as a **cheap early filter**; the **streaming counter** is the check that can't be fooled

## HTTP response caveat (middleware 413)

- A response can't be taken back: once `200` + headers are sent, you can't switch to `413`
- Middleware can return a clean `413` only if the limit trips **before** any response has started
- Fine for form-parsed uploads (body is consumed before the handler responds)
- Can break with streaming designs that send headers early
- Middleware behavior varies by Starlette version, so test it:
  ```bash
  head -c 10000000 /dev/zero > big.bin
  curl -i -F "file=@big.bin;filename=test.png" http://localhost:8000/upload
  ```
  Expect `HTTP/1.1 413`.

## Minimal handler pattern

```python
ext = Path(file.filename or "").suffix.lower()
if ext not in EXT_TO_KIND: raise HTTPException(415)

file_id = uuid.uuid4().hex
tmp_path = UPLOAD_DIR / f".{file_id}.part"
try:
    # stream to disk, enforce MAX_BYTES, sniff magic bytes
    # validate kind == EXT_TO_KIND[ext]
    os.replace(tmp_path, UPLOAD_DIR / f"{file_id}{final_ext}")
except Exception:
    tmp_path.unlink(missing_ok=True)
    raise
```
