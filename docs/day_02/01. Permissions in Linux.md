# File Permissions in Linux

## Reading `ls -la`

```bash
ls -al <dir>
ls -ld <dir>      # the directory itself, not its contents
```

```text
drwxr-xr-x  2 alex staff 4096 Nov 18 10:30 notebooks
-rw-r--r--  1 alex staff 2048 Nov 18 10:32 notes.txt
lrwxrwxrwx  1 alex staff    9 Nov 18 10:33 latest -> notes.txt
```

The columns:

1. **Type and permissions** — `drwxr-xr-x`
    - First character is the type: `-` regular file, `d` directory, `l` symlink, `c` character device, `b` block device, `s` socket, `p` named pipe.
    - The remaining nine characters are three groups of `rwx`: **owner**, **group**, **others**. A `-` means that permission is absent.
2. **Hard-link count** — `2` for a directory (itself plus its `.` entry), `1` for a plain file.
3. **Owner** — `alex`
4. **Group** — `staff`
5. **Size in bytes** — `2048` (use `-h` for `2.0K`). For a directory this is the size of the directory entry, not of its contents.
6. **Last-modified time** — `Nov 18 10:32`
7. **Name** — `notes.txt`, or `latest -> notes.txt` for a symlink.

## Permission categories

| Category | Who |
|---|---|
| **Owner** (`u`) | The user who owns the file |
| **Group** (`g`) | Members of the file's group |
| **Others** (`o`) | Everyone else |

Root bypasses these checks entirely — with one exception: the execute bit still matters for running a file.

## What `r`, `w`, `x` actually mean

The same letters mean different things on a file and on a directory. This is the part that's easy to get wrong:

| Bit | On a file | On a directory |
|---|---|---|
| `r` (4) | Read the contents | **List** the entries (`ls`) |
| `w` (2) | Modify the contents | **Create, delete, rename** entries — even files you don't own |
| `x` (1) | Execute it as a program/script | **Traverse**: `cd` into it, or reach a known path inside it |

Consequences worth internalising:

- A directory with `r` but no `x` lets you see filenames but not open them. Directory with `x` but no `r` lets you open a file if you already know its exact name, but you can't list.
- Deleting a file requires `w` on the **directory**, not on the file. That's why a read-only file in a writable directory is still deletable.
- A script needs `x` to run as `./script.sh`, but not to run as `bash script.sh`.
- Symlink permissions are ignored on Linux — the target's permissions decide.

## Octal representation

Each permission is a number: read = 4, write = 2, execute = 1. Add them per category.

| Symbolic | Octal | Owner | Group | Others |
|---|---|---|---|---|
| `-rw-r--r--` | `644` | 6 (rw) | 4 (r) | 4 (r) |
| `-rw-------` | `600` | 6 (rw) | 0 | 0 |
| `-rwxr-xr-x` | `755` | 7 (rwx) | 5 (rx) | 5 (rx) |
| `-rwx------` | `700` | 7 (rwx) | 0 | 0 |
| `-rwxrwxrwx` | `777` | 7 | 7 | 7 |

`755` = "everyone can read and run it". `644` = "everyone can read it, only I can write it". `777` = "anyone can do anything" — a red flag in review, almost never what you want.

## Changing permissions

```bash
chmod 755 myscript.sh      # octal: owner rwx, group rx, others rx
chmod 644 notes.txt        # owner rw, group r, others r

chmod u+x myscript.sh      # symbolic: add execute for the owner
chmod go-w notes.txt       # remove write from group and others
chmod a+r public.txt       # add read for all (u+g+o)
chmod u=rw,g=r,o= notes.txt  # set exactly: owner rw, group r, others nothing
chmod -R 755 assets/       # recursive — careful with files inside
```

Symbolic mode is `[who][operator][permission]`: who is `u`/`g`/`o`/`a`, operator is `+`/`-`/`=`, permission is `r`/`w`/`x`. It's safer than octal when you only want to change one bit.

Recursive `chmod -R` applies the **same** mode to files and directories — which is wrong for a web tree, where directories need `755` (traverse) but files only need `644`:

```bash
find assets -type d -exec chmod 755 {} +
find assets -type f -exec chmod 644 {} +
```

## Changing ownership

```bash
chown alex notes.txt              # owner
chown alex:staff notes.txt        # owner and group
chgrp staff notes.txt             # group only
chown -R alex:staff /srv/app      # recursive
```

Only root can give a file to another user (`chown` to a different owner fails for non-root, even if you own the file). You can `chgrp` to a group you belong to.

## Special bits (know they exist)

| Bit | Octal | On a directory | On a file |
|---|---|---|---|
| setuid | `4xxx` | — | Runs with the **owner's** privileges (`/usr/bin/passwd`) |
| setgid | `2xxx` | New files inherit the directory's **group** | Runs with the group's privileges |
| sticky | `1xxx` | Only the file's owner (or root) can delete entries — this is how `/tmp` works (`drwxrwxrwt`) | — |

You'll see the `t` in `/tmp`'s mode and `s` in `passwd`'s. Both are deliberate privilege-escalation controls; don't set them casually.

## `umask`

New files and directories don't get `777` — the **umask** subtracts from a default (usually `666` for files, `777` for directories). A umask of `022` produces `644` files and `755` directories.

```bash
umask        # 022 on most systems
umask 077    # new files/dirs private to you
```

## Quick reference

| Task | Command |
|---|---|
| Show the mode of a directory itself | `ls -ld dir` |
| Make a script runnable | `chmod +x script.sh` |
| Make a file private | `chmod 600 .env` |
| Normal web file / directory modes | `644` / `755` |
| Check what a process can actually do | `namei -l /path/to/file` (every hop) |
