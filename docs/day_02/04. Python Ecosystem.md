# Python Ecosystem

Three separate things get conflated when people say "install Python":

1. **The interpreter** — `/usr/bin/python3.12`, one per version, system-wide.
2. **The environment** — an isolated set of installed packages, usually a virtualenv with its own `site-packages`.
3. **The dependency declaration** — `pyproject.toml` (what you want) plus a lockfile (what you got).

You change them with different commands, and only two of the three belong in git.

## Why not just `pip install` system-wide

`pip install` into the system interpreter means:

- Two projects needing different versions of the same library collide.
- You can break the OS package manager's own Python packages.
- Nothing records what the project needs, so a teammate can't reproduce it.

Modern distributions block this on purpose:

```text
error: externally-managed-environment
× This environment is externally managed
```

That error (PEP 668) is the OS telling you to use a virtualenv. Don't reach for `--break-system-packages`.

## Virtual environments

```bash
python3 -m venv .venv          # create it — .venv/ now holds a private interpreter + pip
source .venv/bin/activate      # activate (bash/zsh)
. .venv/bin/activate.fish      # fish
deactivate                     # leave
```

Activation doesn't copy Python. It prepends `.venv/bin` to `PATH`, so `python`, `pip` and any console script installed there resolve to the venv first. `VIRTUAL_ENV` is set as a marker. That's the whole trick — which also means activation is **per shell**: a new terminal is back to the system interpreter until you activate again.

Check which one you're talking to before blaming a missing package:

```bash
which python
python -c "import sys; print(sys.prefix)"   # .../.venv means you're inside it
```

**Never commit `.venv/`.** It contains absolute paths and platform-specific binaries. It is rebuilt, not shared.

## Installing packages

```bash
python -m pip install requests           # into the active environment
python -m pip install -r requirements.txt
python -m pip list
python -m pip freeze > requirements.txt  # exact versions of everything installed
```

Prefer `python -m pip` over bare `pip`: it guarantees the pip belonging to *that* interpreter, which is the single most common cause of "I installed it but Python can't find it".

### Manifest vs lockfile

| File | Answers | Hand-written? |
|---|---|---|
| `pyproject.toml` → `dependencies` | "what does this project need, and within what range" | Yes |
| `requirements.txt` (unpinned) | same, older style | Yes |
| `uv.lock` / `poetry.lock` / pinned `requirements.txt` | "exactly which versions, with hashes, resolved" | No — generated |

`pip freeze` output is a **lockfile**, not a manifest: it pins every transitive dependency, including ones you never asked for, and loses the distinction between direct and indirect. Use it to reproduce an environment, not to declare one.

## `pyproject.toml`

```toml
[project]
name = "backend-onboarding"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "fastapi>=0.115",
    "uvicorn[standard]>=0.32",
    "pydantic-settings>=2.6",
]

[dependency-groups]
dev = [
    "pytest>=8",
    "ruff>=0.7",
]
```

- `requires-python` is a promise to anyone installing it. Pin it to what you actually run, not to "latest".
- `[dependency-groups]` (dev) keeps test and lint tools out of production installs.
- Extras (`uvicorn[standard]`) pull optional dependencies — here the fast event loop and reload support.

## `uv`

`uv` is a drop-in replacement for `pip` + `venv` + `pip-tools`, written in Rust, that also resolves and locks.

```bash
uv venv                        # create .venv (faster than python -m venv)
uv add fastapi uvicorn         # add to pyproject.toml AND install AND update uv.lock
uv add --dev pytest ruff       # dev group
uv sync                        # make the environment match the lockfile exactly
uv run pytest                  # run inside the project env, no activation needed
uv pip install requests        # pip-compatible escape hatch
uv python install 3.12         # manage interpreter versions
```

`uv sync` is the command to reach for on a fresh clone: it reads `uv.lock` and produces the same environment the author had. `uv run <cmd>` removes the "did I activate?" class of bug entirely.

**Commit `uv.lock`.** Not committing it defeats the point — the lockfile is what makes builds reproducible.

## The npm parallel

Same three layers, different names, in case the plan's "pip, npm" comparison comes up:

| Concept | Python | Node |
|---|---|---|
| Manifest | `pyproject.toml` | `package.json` |
| Lockfile | `uv.lock` / `poetry.lock` | `package-lock.json` |
| Installed env | `.venv/` | `node_modules/` |
| Install everything | `uv sync` | `npm ci` |
| Add a dependency | `uv add x` | `npm install x` |
| Run a script | `uv run pytest` | `npx eslint` |
| Version pinning | `requires-python` | `"engines": { "node": ">=20" }` |

Both commit the manifest **and** the lockfile, and both gitignore the installed directory.

## What goes in git

```text
commit:      pyproject.toml, uv.lock, .python-version (optional)
gitignore:   .venv/, __pycache__/, *.pyc
never:       .env (secrets), any installed environment
```

## Quick checks

```bash
which python                  # is it the venv?
python -m pip -V              # which pip, which site-packages
uv tree                       # resolved dependency graph
uv lock --check               # lockfile in sync with pyproject.toml
```
