# What are signals?

A signal is a notification sent to a process or thread, by the kernel, hardware, or another process, saying an event occurred. It interrupts the program's normal flow, so signals are also called _software interrupts_.

### **Synchronous (caused by the program's own instruction)**

- Raised by a CPU fault while running a specific instruction.
- Examples: `SIGSEGV` (invalid pointer), `SIGFPE` (divide by zero), `SIGILL` (illegal instruction).
- Always sent to the exact thread that ran the faulty instruction.

### **Asynchronous (caused by something external)**

- Arrives from outside the program's own control flow.
- Examples: `SIGINT` (Ctrl+C), `SIGTERM` (another process asks it to terminate), `SIGALRM` (timer expired).
- Can go to the whole process, where any thread not blocking the signal may receive it, or to one specific thread via `pthread_kill(3)`.

# Common Practices and Patterns

### Graceful Shutdown Workflow (SIGTERM with SIGKILL Timeout)

A standard operational pattern is to dispatch `SIGTERM`, wait for a reasonable grace timeout period (e.g., 10 to 30 seconds), and only escalate to `SIGKILL` if the process remains stuck or unresponsive:

```text
supervisor                    process
   |  SIGTERM (15)  ---------->  handler runs:
   |                             - stop accepting new work
   |                             - finish in-flight requests
   |                             - close DB pool, flush logs
   |  <---------- exit 0         - release the port
   |
   |  ...wait up to N seconds...
   |
   |  SIGKILL (9)   ---------->  kernel tears it down. No handler.
   |                             Open sockets reset, locks may be left stale.
```

What each signal makes possible:

- **SIGTERM is a request, not an order.** A well-written server catches it, drains in-flight work, runs its shutdown hooks, closes the listening socket, and exits `0`. In FastAPI/uvicorn this is the lifespan shutdown: stop accepting connections, let active requests finish, close resources.
- **SIGKILL cannot be caught.** The kernel destroys the process mid-instruction. No flush, no cleanup, no exit code. In-flight requests are reset, and anything the process held (temp files, advisory locks, half-written output) is left exactly as it was.

Who enforces the timeout (so you rarely type this by hand):

| Supervisor | Setting | Typical default |
|---|---|---|
| `docker stop` | `--stop-timeout` / `-t` | 10 s, then SIGKILL |
| Kubernetes | `terminationGracePeriodSeconds` | 30 s, then SIGKILL |
| systemd | `TimeoutStopSec=` | 90 s for services |
| uvicorn | `--timeout-graceful-shutdown` | waits for in-flight requests, then exits |

Doing it manually:

```bash
kill -TERM 1234          # ask nicely
sleep 10
kill -0 1234 2>/dev/null && kill -9 1234   # -0 tests existence without signalling
```

Why the order matters beyond "politeness":

- A SIGKILL during a DB transaction is *safe* — the database rolls back. But side effects outside the transaction are not: an email already sent, a third-party API already charged, a message already published to a queue. Those need idempotency (Day 4) rather than a shutdown hook.
- A SIGKILL while holding an advisory lock leaves a stale lock file that blocks the next start.
- A SIGKILL to a process writing a temp file leaves a `.part` file behind — which is why upload code publishes with `os.replace` and cleans up on exception.

The grace period should be **slightly longer than your slowest request**. Shorter means you're routinely killing work you asked to finish; much longer means deploys crawl.

### Zero-Downtime Configuration Reload (SIGHUP)

Long-running system daemons—including web servers (Nginx, Apache), proxy managers (HAProxy), and system supervisors (`systemd`)—conventionally repurpose `SIGHUP` to trigger online configuration reloads:

- When `SIGHUP` is received, the master process parses and validates new configuration files from disk.
- If the configuration is valid, it spawns new worker processes with the updated settings.
- It then instructs old workers via `SIGTERM` or `SIGQUIT` to finish processing active connections before shutting down.
- If the configuration file has a syntax error, the master logs an error and continues running with the previous valid configuration, ensuring zero downtime.

```
# Reload Nginx web server configuration without dropping active connections
$ sudo systemctl kill -s HUP nginx
# Or directly via pkill
$ sudo pkill -HUP nginx
```

# Inspecting processes and ports

You can't signal what you can't find. "Which process owns port 8000?" is a daily question once a dev server is involved.

### Processes

```bash
ps aux                 # every process, BSD syntax
ps -ef                 # every process, UNIX syntax (PPID visible)
pgrep -af uvicorn      # match name + show full command line
top                    # live CPU/memory, press M for memory, P for CPU
```

The `ps aux` columns that matter:

| Column | Meaning |
|---|---|
| `USER` | Who owns it (you can only signal your own without privileges) |
| `PID` | The number `kill` takes |
| `%CPU` / `%MEM` | Snapshot, not an average |
| `STAT` | `R` running, `S` sleeping, `D` uninterruptible sleep (usually I/O), `Z` zombie, `T` stopped |
| `TIME` | Total CPU time consumed, not wall-clock |
| `COMMAND` | The full command — check this before killing anything by name |

A `D` state process ignores signals until the I/O completes; `Z` means it's already dead and its parent hasn't reaped it (the fix is fixing the parent, not killing the zombie).

### Ports

```bash
ss -tulpn                  # listening TCP/UDP sockets, with the owning process
ss -tulpn | grep :8000     # one port
lsof -i :8000              # who has port 8000 (needs privileges for other users' processes)
fuser 8000/tcp             # just the PID(s)
```

`ss` flags: `-t` TCP, `-u` UDP, `-l` listening only, `-p` show process, `-n` numeric ports (no name lookup). `netstat` is the older equivalent and is deprecated on most distributions.

### The full loop

```bash
uvicorn app.main:app --port 8000      # start something that holds the port
ss -tulpn | grep :8000               # PID=42111, name=uvicorn
kill -TERM 42111                     # graceful: uvicorn drains and exits
```

Common traps:

- **"Address already in use"** means a previous instance survived — find it with `ss`/`lsof` rather than guessing PIDs.
- `lsof -p` shows nothing for root-owned processes unless you run it with `sudo`.
- Inside a container the port belongs to a process in the container's network namespace — `ss` on the host won't show it. Use `docker exec` or `docker compose logs` instead.
- Killing by name (`pkill uvicorn`) can hit a colleague's process on a shared box; kill by PID when you have the number.

# Usage

### 1. `kill` (Targeting by PID or Process Group)

The `kill` command dispatches a signal to a process by its Process ID (PID). If no signal is specified, `kill` defaults to sending `SIGTERM` (signal 15).

```
# Graceful termination (defaults to SIGTERM / 15)
$ kill 1234
 
# Explicit signal by name or number
$ kill -SIGTERM 1234
$ kill -15 1234
 
# Immediate force kill (SIGKILL / 9)
$ kill -9 1234
 
# Send a signal to an entire Process Group (negative PID)
$ kill -TERM -1234
```

### 2. `pkill` (Targeting by Pattern or Command Line)

Part of the `procps` package, `pkill` matches processes using regular expressions against command names or full command lines (`-f`).

```
# Send SIGTERM to all processes whose name matches "nginx"
$ pkill nginx
 
# Send SIGHUP to a Python worker matching a specific script path
$ pkill -HUP -f "/opt/app/worker.py"
 
# Send SIGKILL only to processes owned by a specific user
$ pkill -9 -u www-data php-fpm
```

### 3. `killall` (Targeting by Exact Process Name)

`killall` dispatches a signal to all running instances of a specified binary name.

```
# Gracefully terminate all running instances of firefox
$ killall firefox
 
# Forcefully kill all instances of a stuck background service
$ killall -9 celery
```

### Terminal Keyboard Shortcuts

When working in an interactive terminal session, the Linux TTY driver maps specific control keys directly into signal generation for the foreground process group:

|Shortcut|Signal Generated|Meaning and Effect|
|:-:|:-:|:--|
|**`Ctrl + C`**|`SIGINT`|Interrupt: Requests foreground application to stop cleanly.|
|**`Ctrl + \`**|`SIGQUIT`|Quit: Halts the process immediately and instructs the kernel to generate a core dump.|
|**`Ctrl + Z`**|`SIGTSTP`|Terminal Stop: Suspends the foreground process, moving it into the shell background where it can be inspected via `jobs` and resumed via `fg` or `bg`.|
