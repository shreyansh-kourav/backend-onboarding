# Internet

## DNS

### Recursive Resolvers

> **This does the to and fro motion of asking the next dns server in chain. The referalls are usually NS records**

- Your computer typically runs a lightweight **stub resolver**: it sends the question to a recursive resolver and **passes the reply back to the app**. The recursive resolver—often run by your ISP, workplace, or a public DNS provider—does the full lookup and caches results.

### Root Servers

1. There are 13 root server identities (urls - a through m) and behind that there are multiple instances balancing the traffic
	1. examples - `a.my-dns-server.net`
2. Each serves the same root-zone information - a map of top-level domains such as `.com` and `.org` to know which next DNS servers to ask
3. These are advertised through **anycast** - every instance part of a single root server have a single IP and internet routing usually refers to the one closest because the way protocols are designed (BGP)


> **Caching is done at multiple levels - client, recursive resolvers, etc**

| Record type | Response Format |
| ----------- | --------------- |
| A           | IPv4 Address    |
| AAAA        | IPv6 Address    |

# Server

## TCP

1. Both the client and server performs a 3-Way handshake at connection establishment and a 4-way handshake at connection termination (ideally)
2. Connection Endpoints are identified by a combination of **IP address** and **port numbers**
3. TCP uses two related controls:
	- Flow control protects the receiving device. It advertises how much incoming data it can currently buffer; the sender limits how much unacknowledged data it sends accordingly.
	- Congestion control protects the network path. The sender adjusts its sending rate based on signs of congestion, such as loss or changing acknowledgments and timing.

```
Client                            Server
  SYN, initial sequence x  ────>
		                   <────  SYN-ACK, sequence y, ack x+1
  ACK, ack y+1             ────>
```

## TLS

1. TLS is the layer that secures the connection TCP has established. It provides encryption, checks that data hasn’t been altered in transit, and usually lets the browser verify the server’s identity.
	- **ClientHello**: The client proposes TLS options, names supported cryptographic methods, and sends a temporary key share. It also commonly includes the hostname it wants to reach, using SNI, so a server hosting multiple sites can select the right certificate and site.
	- **ServerHello**: The server selects compatible options and sends its own key share. Using the two key shares, both sides independently derive matching secret keys; the secret itself isn’t sent across the network.
	- **Certificate and identity check**: The server sends a certificate, usually with a chain leading to a trusted certificate authority. The browser checks that it’s valid, matches the requested hostname, and is trusted. The server also proves it controls the corresponding private key. In TLS 1.3, these later handshake messages are encrypted.
	- **Finished messages**: Both sides verify that the handshake hasn’t been tampered with and confirm they derived the same keys. Then protected application data can flow.

```
Client                                      Server
  ClientHello ────────────────────────────>
             <──────── ServerHello + key share
             <──────── Encrypted handshake messages,
                        including certificate and Finished
  Finished ──────────────────────────────>
  Encrypted application data ⇄
```

> TLS uses public-key cryptography during setup to authenticate the server and establish shared secrets. It then derives **symmetric keys** for encrypting and authenticating the actual data, because symmetric encryption is efficient for ongoing communication.

> TLS protects data between the two TLS endpoints not the metadata; also if a *CDN or reverse proxy terminates TLS*, that endpoint can see the decrypted request before forwarding it onward

> The certificate helps confirm that the connection is to the domain named in the URL; it doesn’t guarantee the site itself is honest or safe

## HTTP

1. HTTP is the application-level protocol that says what resource the client wants and what the server returns
2. A HTTP request can contain Headers, Body, Path, Methods, etc

A simplified HTTP request might look like:

```http
GET /products HTTP/1.1Host: www.example.comAccept: text/html
```

A simplified response is:

```http
HTTP/1.1 200 OKContent-Type: text/html
<html>...</html>
```
