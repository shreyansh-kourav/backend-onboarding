# REST notes

## Resources

- A **resource** is any "thing" the API exposes: a user, an order, a collection of orders.
- Each resource has a unique identifier (a URI). The client works with **representations** of it (usually JSON), not the thing itself.
- Collection vs. item: `/orders` is the collection, `/orders/42` is one item.

## Nouns in URLs, verbs in methods

The URL says **what**, and the HTTP method says **what to do**.

|Bad (verb in URL)|Good (noun + method)|
|---|---|
|`POST /createUser`|`POST /users`|
|`GET /getOrder?id=42`|`GET /orders/42`|
|`POST /deleteOrder/42`|`DELETE /orders/42`|

Conventions:

- Use plural nouns (`/users`) and lowercase, hyphenated paths.
- Use nesting for relationships: `/users/7/orders`.
- Filtering, sorting and paging go in the query string: `/orders?status=paid&sort=-date`.

## Methods

| Method | Purpose                    | Safe | Idempotent     |
| ------ | -------------------------- | ---- | -------------- |
| GET    | Read                       | ✅    | ✅              |
| POST   | Create / trigger an action | ❌    | ❌              |
| PUT    | Replace the whole resource | ❌    | ✅              |
| PATCH  | Partial update             | ❌    | Not guaranteed |
| DELETE | Remove                     | ❌    | ✅              |

- **Safe** means it doesn't change server state.
- PUT replaces the full resource. PATCH changes only the fields you send.

## Statelessness

- Each request must contain **everything the server needs** to process it. The server stores no client session state between requests.
- Authentication therefore goes on every request, via a token (e.g. `Authorization: Bearer <token>`), not a server-side session.
- **Benefits:** easy horizontal scaling (any server can handle any request), simpler failure recovery, and better cacheability.
- **Costs:** slightly larger requests, and the client carries the state.
- Statelessness refers to _session_ state. The resources themselves (data in the database) are still stored.

## Idempotency

**Definition:** making the same request N times leaves the server in the same state as making it once. The response may differ between calls, but the server's state doesn't.

Examples:

- `PUT /users/7 {name: "Asha"}` sets the name to Asha, so repeating it changes nothing further. ✅
- `DELETE /orders/42` removes the order. The second call may return 404, but the state is the same: the order is gone. ✅
- `POST /orders` creates a new order each time, so 3 calls make 3 orders. ❌
- `PATCH` is idempotent if it says "set status = shipped", but not if it says "increment quantity by 1".

**Why it matters:** networks fail. If a client times out, it can safely **retry** idempotent requests without causing duplicates.

**Making POST safe to retry:** the client sends an `Idempotency-Key` header (a unique ID). The server remembers it and returns the original result for repeats. Payment APIs commonly do this.

## Versioning

### Why version at all

- A **breaking change** is anything that can make existing clients fail: removing or renaming a field, changing a type, changing semantics, making an optional param required.
- **Non-breaking** (additive) changes need no new version: adding a new field, a new endpoint, or a new optional parameter. Clients should ignore fields they don't recognize (the _tolerant reader_ pattern).
- Versioning lets old clients keep working while new ones adopt the changed contract.

### Where to put the version

|Approach|Example|Pros|Cons|
|---|---|---|---|
|**URL path**|`GET /v2/orders/42`|Obvious, easy to test in a browser, easy to route and cache, easy to log|Version becomes part of the resource's URI, which purists say breaks "one resource = one URI"|
|**Query param**|`GET /orders/42?version=2`|Easy to add, optional with a default|Easy to forget, messy with caching, feels bolted on|
|**Custom header**|`API-Version: 2`|Clean URLs|Hidden from the URL, harder to test by hand, caches must vary on the header|
|**Content negotiation (media type)**|`Accept: application/vnd.myapi.v2+json`|Most "RESTful": the version is a property of the _representation_|Most complex for clients and tooling|

- **URL versioning is the most common** in practice (Stripe uses date-based versions via a header, but most public APIs use `/v1/`, `/v2/`).

### Version granularity

- **Major only** (`v1`, `v2`) is typical for public APIs.
- **Date-based** (e.g. `2026-11-01`) is used by some providers: each account is pinned to the date it first integrated and upgrades deliberately.

## Deprecation

Retiring an old version should be a managed process, not a surprise.

1. **Announce** early: changelog, email, docs, developer portal.
2. **Signal in responses** using headers:
    - `Deprecation: true` (or a date) marks the endpoint as deprecated.
    - `Sunset: Sat, 31 Jul 2027 00:00:00 GMT` gives the date it will stop working (RFC 8594).
    - `Link: <https://api.example.com/docs/migrate-v2>; rel="deprecation"` points to the migration guide.
3. **Give a migration window**: commonly 6 to 12+ months for public APIs.
4. **Monitor usage** of the old version to see who is still on it and contact them directly.
5. **Brown-out** (optional): briefly turn the old version off to flush out forgotten clients.
6. **Sunset**: finally return **410 Gone** (or redirect with guidance) for the retired version.
