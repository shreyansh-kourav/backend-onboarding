# Trust Boundaries

## The core idea

- A **trust boundary** is any point where data crosses from a less-trusted zone into a more-trusted one: browser to server, public internet to internal network, one service to another, third-party API to your system.
- **Rule:** anything that crosses a boundary is untrusted until your backend validates it. Client-side checks are only for user experience, never for security, because an attacker can skip the UI and call the API directly.
- Validate on the server, on **every** request (this ties back to statelessness: each request must prove itself).

## 5 inputs never to trust

### 1. Request body and parameters (including query strings and path params)

- Anything the client sends can be missing, malformed, oversized, or hostile.
- **Risks:** SQL injection, command injection, NoSQL injection, XSS (when later rendered), mass assignment (client sets `isAdmin: true` in the body).
- **Defenses:**
    - Validate **type, format, length and range** against a schema, preferably with an allowlist.
    - Use **parameterized queries** and never build SQL by string concatenation.
    - Bind only expected fields to your model (explicit allowlist), so extra fields are dropped.
    - Escape output for its context (HTML, JS, URL).

### 2. Headers and cookies

- Headers like `Host`, `X-Forwarded-For`, `Referer`, `User-Agent`, `Origin` and custom headers are client-controlled and can be forged.
- Cookies can be edited or replayed by the client.
- **Risks:** spoofed IPs defeating rate limits or audit logs, host header poisoning, header injection (CRLF), session tampering.
- **Defenses:**
    - Only trust `X-Forwarded-*` headers when set by **your own** proxy, and strip them at the edge otherwise.
    - Sign or encrypt cookies, and set `HttpOnly`, `Secure`, `SameSite`.
    - Never rely on `Referer` or `Origin` alone for authorization.

### 3. Identity and authorization claims from the client

- Examples: a `userId` in the body or URL, a `role` field, a price or discount sent by the client, or a JWT you haven't verified.
- **Risks:** **IDOR / broken object-level authorization** (changing `/orders/42` to `/orders/43` to read someone else's order), privilege escalation, price tampering.
- **Defenses:**
    - Derive the user from the **verified token or session**, not from a client-supplied field.
    - **Check authorization on every object access**: "does _this user_ own _this resource_?"
    - Verify JWT signature, expiry (`exp`), issuer and audience. Never accept `alg: none`.
    - Compute prices, totals and permissions on the server.

### 4. Uploaded files

- Filename, extension, MIME type (`Content-Type`) and contents can all be lies.
- **Risks:** malware, web shells, path traversal (`../../etc/passwd`), zip bombs, SVG/HTML with scripts, huge files exhausting disk.
- **Defenses:**
    - Enforce **size limits**, and allowlist extensions and detected content types (check magic bytes, not just the header).
    - Generate your own filenames and store files **outside the web root** (or in object storage).
    - Serve user content from a separate domain with safe headers (`Content-Disposition`, `X-Content-Type-Options: nosniff`).
    - Scan for malware where appropriate.

### 5. Data from other systems (third-party APIs, webhooks, internal services, the database)

- It's easy to assume "it's from another service, so it's safe." That's wrong.
- **Risks:** forged webhooks, compromised or buggy upstream services, **SSRF** (your server fetches a user-supplied URL and hits internal resources like cloud metadata endpoints), stored malicious data that is later reused (**second-order injection**).
- **Defenses:**
    - Verify **webhook signatures** (HMAC) and timestamps to block replays.
    - For user-supplied URLs: allowlist hosts, block private and link-local IP ranges, limit redirects.
    - Validate upstream responses against a schema just like user input.
    - Treat stored data as untrusted when you output it or use it in new queries.

## Cross-cutting practices

- **Validate early, reject by default** (allowlist over denylist).
- **Canonicalize before validating** (decode, normalize) so encoding tricks don't bypass checks.
- **Least privilege:** the DB account, service tokens and file permissions should allow only what's needed, to limit the damage when validation fails.
- **Rate limit and cap payload sizes** to stop abuse and resource exhaustion.
- **Don't leak internals** in errors: log details server-side, return generic messages (ties to 400 vs 500 from the REST notes).
- Remember **CSRF**: cookie-based auth means the browser attaches credentials automatically, so state-changing requests need CSRF protection (tokens, `SameSite`).
