# Headers, Cookies & Trust (FastAPI)

## First principle
The network has no identity. Every header, cookie, and body field is **text the client wrote**, so it's a *claim*, not a fact.

Three questions for any value in your code:
1. **Who could have written this?** (client, my proxy, my DB, my config)
2. **If they lied, what's the worst outcome?**
3. **Which proof do I have?** If none, it can't drive a security decision.

## Fact vs claim
- **Fact:** the TCP source address (socket peer). Hard to fake, because replies must return to the sender.
- **Claim:** everything else the client sends.
- Caveat: behind a proxy, load balancer or NAT, the socket peer is the proxy or gateway, not the client — so even the "fact" stops being the client's identity. Source spoofing is impractical when a handshake is required; that guarantee does not exist for UDP.

## Three ways a claim becomes trustworthy
1. **A secret proves it:** signed or encrypted cookie, JWT signature
2. **A trusted party overwrote it:** your own proxy replaces `X-Forwarded-For`
3. **You verify against your own records:** DB lookup, allowlist, config

## How a server uses headers (request flow)
| Stage | Headers | Purpose |
|---|---|---|
| Routing | `Host` | Which site/app gets the request |
| Body parsing | `Content-Length`, `Transfer-Encoding`, `Content-Type` | Where the body ends and how to parse it |
| Identity | `Cookie`, `Authorization` | Who the caller is (verify the signature or look it up) |
| Negotiation | `Accept`, `Accept-Language`, `Accept-Encoding` | Preferences for format, language, compression |
| Caching | `If-None-Match`, `If-Modified-Since` | "I already have this version" leads to 304 |
| Context | `X-Forwarded-For`, `X-Forwarded-Proto`, `User-Agent`, `Origin`, `Referer` | Client IP, original scheme, logging, CSRF check |
| Response | `Set-Cookie`, `Location`, `Cache-Control`, `Content-Type`, security headers | Instructions to the browser |

Wherever the server **acts** on a header, ask whether a lie there causes harm, and put a check in that spot.

## Header by header
| Header | Who really writes it | Use it for | Fix / rule |
|---|---|---|---|
| `X-Forwarded-For` | Client, unless proxy overwrites | Client IP, rate limits, audit logs | Proxy **overwrites** it (`proxy_set_header X-Forwarded-For $remote_addr;`). App trusts it only from the proxy (`uvicorn --proxy-headers --forwarded-allow-ips=<proxy>`). Read `request.client.host`. Firewall the app port. |
| `Host` | Client | Routing only | `TrustedHostMiddleware` allowlist. Build reset or absolute links from config (`PUBLIC_BASE_URL`), never from `Host`. nginx default server rejects unknown hosts. |
| `Origin` | Browser sets it and JS can't change it, but `curl` can forge it | CSRF defense in depth | Check against an allowlist on non-safe methods. Pair with `SameSite` and CSRF tokens. |
| `Referer` | Browser, often stripped, forgeable | Analytics | Never use for security. |
| `User-Agent`, custom headers | Client | Logging | Never for security decisions. Sanitize before logging. |
| `Cookie` | Client can edit or replay | Session ID | Sign or encrypt, or keep a random session ID with data server-side. |

## Host header poisoning / cache poisoning
- Never build absolute URLs from `Host` — password-reset and email-verification links are the classic exploit.
- `X-Forwarded-Host` is the same claim wearing a different name.
- A cache in front of the app can be poisoned if it varies on a header the app never validated: send `Vary` for everything you genuinely vary on, and have the proxy strip unknown `X-Forwarded-*` headers at the edge.

## Authorization
Comes from **proof of identity** (valid session or token) plus a **permission check on the specific resource** in your DB. Never from `Referer` or `Origin`.

## Cookies
- Flags: `HttpOnly`, `Secure`, `SameSite=Lax` (or `Strict`), `__Host-` prefix (or `__Secure-` when a `Domain` is genuinely needed)
- `SameSite=None` is only honoured together with `Secure`, and it re-opens cross-site sending — that combination needs a CSRF token, not just the attribute.
- Signing stops **tampering**. It does **not** stop **replay** of a stolen valid cookie.
- Limit replay damage:
  - Server-side sessions, so logout or a password change revokes them
  - Short lifetime plus idle timeout
  - Rotate the session ID on login and privilege change
- Don't hard-bind sessions to IP or User-Agent, because it breaks mobile users.
- `CORSMiddleware` is not access control. It only tells browsers whether pages may read responses.

## CRLF / header injection
- Same principle applied to **output**: untrusted text must not land where it's interpreted as structure.
- Modern servers mostly reject CR/LF in header values, but still:
  - No raw user input in `Location`, `Set-Cookie`, `Content-Disposition`
  - Validate redirect targets (relative paths only, no `//`)
  - Encode filenames: `filename*=UTF-8''{quote(name)}` plus an ASCII `filename="..."` fallback, with quotes and CR/LF stripped from both
  - Log as structured JSON to prevent log injection

## Response-side security headers

Same "who wrote this" question pointed the other way: these are claims the server makes to the browser, and they only work because the browser enforces them.

| Header | Value | Why |
|---|---|---|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains; preload` | After the first HTTPS visit, never downgrade. Meaningless if served over plain HTTP. |
| `Content-Security-Policy` | `default-src 'none'` for user content; a tight allowlist for the app | Stops injected script from executing |
| `X-Content-Type-Options` | `nosniff` | The browser must not guess a type and execute it |
| `X-Frame-Options` / CSP `frame-ancestors` | `DENY` / `'none'` | Clickjacking |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Don't leak paths and query strings to third parties |
| `Cache-Control` | `no-store` on authenticated responses | Keeps private data out of shared caches |
| `Vary` | whichever headers you actually vary on | Prevents cache poisoning via a header |

## Rate limiting
- Resolve the real IP first (see `X-Forwarded-For` above)
- Limit by IP **and** by account (attackers rotate IPs)
- Keep IP limits generous (NAT shares IPs). Group IPv6 by `/64`.

## Checklist
- [ ] Proxy overwrites `X-Forwarded-For`. App port firewalled.
- [ ] uvicorn `--forwarded-allow-ips` set to the proxy only (not `*` unless firewalled)
- [ ] Client IP from `request.client.host`, not the raw header
- [ ] `TrustedHostMiddleware` + nginx default-reject server block
- [ ] Sensitive links built from config, not `Host`
- [ ] No raw user input in response headers. Redirects validated.
- [ ] Cookies: `HttpOnly`, `Secure`, `SameSite`, `__Host-`, server-side sessions, rotation
- [ ] `SameSite=None` only with `Secure` plus a CSRF token
- [ ] Response headers: HSTS, CSP, `nosniff`, `frame-ancestors`, `Referrer-Policy`
- [ ] `Cache-Control: no-store` on authenticated responses; `Vary` where it matters
- [ ] Authorization via session/token + resource permission check
- [ ] `Origin` check as extra layer, with CSRF tokens on sensitive actions
- [ ] Rate limits by IP and account
